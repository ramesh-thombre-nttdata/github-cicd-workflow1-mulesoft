The Hype vs Reality:
before we go much further, we should set some expectations for what agentic systems can and can't do.
- Many folks are eager to take advantage of the advances in AI by developing elaborate AI systems that try to do it all.
- However, the truth is that it's better to try and keep the AI tools you develop as simple as possible.
- Frontier AI models are capable of a great deal.
- A task you might imagine would require a sophisticated agent might actually only  need a single prompt.
- with that said, when agentic systems are applied at the correct place in the workflow perform reliably, and are designed thoughtfully, they can lead to a tremendous boos in productivy.
- With correct understanding of tooling and systems design patterns,agetns can carry out that would have taken hours for human workers in a matter of minutes.
- But it's imp to remember that these productivity gains only appear when the agents are deployed for the right problem with the right design.

Do you need agents?
Here are a few questions to ask yourself when considering the development of an AI agent.
- first of all, take a hard look at the scope of your problem and honestly consider whether you need an agent at all.
1. Would a single, well-tuned prompt accomplish your task?
- Assuming your exp in prompt engg and working with LLMs, could you feasibly imagine your task being carried out with a sinle well written prompt?
- If you are not sure, you should try it out and see what you get.
- I fyou can clearly see a path toward automating more of the AIS interactions, start slow and build the complexity step by step.

2. Would a newer, stronger model make your app better or make it obsolete?
- another question to ask is, would the release of a newer, more capable model make my agentic application better or obsolete?
- since the release of gpt 3, many AI applications have gone extinct as models increased in capabilities.
- Don't invest significant time or money in an agent if you feel you're at risk of this as well.

How should Choosing between workflows and autonomous agents:
conside the following factors:
1.  Task complexity:
- for well defined tasks with predictable steps, use workflows
- how complex is the task?
- could you reliably list out subtasks in a way that would fit the single taks of the job each time. If so, consider a workflow.
- For open ended problems, use autonomous agents
- if the task is more complex and open ended, requiring an unpredictable number of subtasks, choose an agent.

2. How predictable is the tasks? (Predictability vs Flexibility)
- If you need consistency, use workflows
- are there situations in which a predefined set of steps would be found lacking?
- Does the tasks require adapting to a variety of changing conditions?
- again, static choices should follow work flows
- if you need adaptability for various scenarios, use agents.
- while more unpredictable tasks should follow agetns.

3. what kind of resources are you capable of devoting to the tasks?(Cost/Latency Awareness)
- Autonomous agents typically have higher latency and costs
- As predictable scripted sets of API calls, work flows have a more predictable cost and latency.
- Agents, however, may call frontier language models and unpredictable number of times and take a long time to execute. 
- so you should make sure that your returns on investment with them are worth it.

Agent types:
- diff types of ai agents, each designed to perform different tasks.
- six different types agents
1. Simple Reflex: small set of takes actions, but based on very specific inputs.
- limited actions
- alters behaviours based on experience by chaning internal parameters.
- Provide basic automated support for tasks based on predefined rules and immediate data
- Used in places where routine tasks can be automated.
- examples include: service chatbots, appointment scheduling
2. Model-based Reflex:
- use an internal model of the world based on perceptions and history.
- that model is used to make decisions, take action, and consider thow their actions impact the world.
- examples include: autonomous vehicles, robotics, smart home systems
3. goal-based reflex:
- Driven by explicit objectives to achieve
- they plan actions using a world model to reach goals
- Examples include: project management software, smart thermostats, robotic vaccum cleaners

4. Utility-based:
- choose actions that are designed to maximize utility
- they consider multiple goals and trade-offs based on value
- Examples include: financial trading systems, personalized recommender systems, resource allocation systems.

5. Hierarchical:
- handle complex tasks by breaking them down into multiple levels.
- the top level defines goals, the mid-levels plan, and the low-level executes actions
- Examples include intelligent personal assistant, automated manufacturing systems

Learning:
- Improve the performance over time through experience and data.
- alter behaviour based on experience by changing internal parmaters or strategies.
- exampels include, virtual assistants, fraud detection systems, adaptive control systems.

Langgraph end to end workflow:
Overiview: build a Graph:
1. define the state
- create a single object that stores all the key data the Graph will use and updates
- this state acts as the "source of truth for every part of the graph"
2. Create the nodes
- build each step of the process as a simple python function
- each node function can read and make changes to the state
3. Add the edges:
- connect nodes together by adding direct links or by setting rules for which node should run next
- these path control how information flows from one step to another

- state acts as dictionary.
4. compile the graph
- start building and compile when ready 
- this puts all the nodes and edges together into a working graph
5. visualize & run
- generate flowchart to see the graph structure
- run the graph using invoke or stream for step by step output

- it is dynamic and keeps changing as the graph runs
- the state holds all critical information needed over time like context, conversation history, or flags.
- it is possible to store many types of dta in the state, such as 
  - a list of messages
  - a dictionary

What is a Neural Network Architecture?
Neural networks are the foundation of modern artificial intelligence, powering everything from text generation to language translation and image recognition. Think of a neural network as a digital brain that learns patterns from data, much like how we learn from our experiences to speak, understand language, and recognize faces.

At its core, every neural network architecture consists of three fundamental components that work together: layers, parameters, and forward pass. These components determine how data flows through the network to train it and generate predictions.

Let’s define each component:

Layers: The fundamental building blocks of any neural network architecture. We start with an input layer that takes in the data, hidden layers that process the data, and the output layer that generates the prediction. Each layer contains a collection of artificial neurons that process information.

Parameters: There are two main parameters: weights and biases. Weights control the strength of connections between neurons across different layers, while the bias term provides more flexibility in learning complex patterns. During training, the network learns to update and adjust these parameters through backpropagation.

Forward Pass: The process by which the input data travels through the network layers, being transformed by the weights, biases, and activation functions to generate an output.

In this lesson, we’ll explore how these core components make up three foundational neural network architectures: Multi-Layered Perceptrons (MLPs), Convolutional Neural Networks (CNNs), and Recurrent Neural Networks (RNNs).

Multi-Layered Perceptrons (MLPs): consist of fully connected layers, where every neuron in one layer connects to every neuron in the next

Use cases: regression and classification problems involving tabular data
Limitations: Treat all input features equally, and don’t consider spatial relationships (important for images) or temporal relationships (important for sequences).
Convolutional Neural Networks (CNNs): Specifically designed for processing images and spatial data, using convolutional layers that contain grid-like filters to scan (slide through) the image and detect patterns.

Use cases: computer vision tasks like image classification and object segmentation
Strengths: captures spatial hierarchies, like detecting small patterns (edges or corners) and combining them into larger, more complex patterns (faces or objects)
Recurrent Neural Networks: Specifically designed for processing sequential data (like words in a sentence or time series).

Use cases: sequential tasks like text generation, text classification, and forecasting
Strengths: captures long-term temporal relationships within sequences

Let's now consider LangGraph at a glance. LangGraph is designed specifically for modeling agent workflows as graphs. Each node represents a step in reasoning or action, and edges define the flow of decisions or data. LangGraph builds on LangChain's primitives. It uses LangChain tools, chains, memory, and agents wrapped inside a graph structure that adds state, flow control, and persistence.

LangGraph is fully open-source and written in Python. It's easy to install, extend, and integrate into existing LangChain projects, making it accessible to developers and researchers alike. LangGraph shines when you need to manage state across multiple steps, decisions, or retries. It's a perfect fit for complex agents that think, plan, act, and loop intelligently.

Let us now consider why LangGraph exists. Real agents aren't linear. They loop, branch, retry, and adapt. To build such agents, you need more than a sequence of prompts. You need memory and flow control. Retry logic and branching matter. For example, if an API call fails due to a network issue or rate limit, the agent should automatically retry instead of crashing.

Similarly, branching logic allows the agent to choose different paths based on intermediate results, like following a different sequence if a user changes their request or if a tool returns unexpected output. Without this kind of control, the agent's behavior becomes brittle and unpredictable. LangGraph provides this power by modeling the agent as a stateful graph with memory at each node and flexible edges between steps. This makes it easier to build robust adaptive workflows that reflect how real-world tasks evolve.

We'll now outline some core concepts behind LangGraph. In LangGraph, nodes represent logical steps like calling an LLM or using a LangChain chain. Edges define how states connect based on output conditions or internal variables. Each node can access stateful memory, letting the agent recall facts, past steps, or external results.

This setup makes loops and retries incredibly easy to implement, something that's hard with standard chains. LangGraph is not a competitor to LangChain, it extends it. You can use LangChain tools, memory systems, and even agents directly inside your LangGraph nodes. That means you can reuse your existing chains and pipelines inside graphs to add structure without reengineering your whole stack.

LangGraph is especially powerful for advanced LangChain users who want more structure, robustness, and reasoning control. Let's now consider some use cases. Even simulation environments where agents observe, act, and loop benefit from graph-based control. Let's now peek at LangGraph in action through a simple but powerful example. The second node is act which handles the tool_use_step. Now, we define how these nodes connect. We add an edge from plan to act. This means after planning, the agent moves on to take action. Then we add another edge from act back to plan. This creates a retry loop, so if the tool action needs to be adjusted or fails, the agent can go back and replan.

And that's it. With just a few lines of code, we've built an agent that can plan, act, and retry. Thanks to LangGraph's simple but flexible graph-based design. Understanding state flow is crucial because this is how information accumulates, transforms, and becomes more valuable as it moves through your graph. Let's start with a deep dive into what state really is. State is a shared data structure that all nodes can access and modify.

It's defined using TypedDict, which is Python's way of specifying exactly what fields your state contains and what types they should be. Think of state as the memory of your workflow; it remembers everything that has happened so far. Why does state matter so much? First, it carries information between nodes. Third, it enables nodes to build on previous work. Node C doesn't start from scratch; it leverages everything nodes A and B already found. Therefore, state is what makes your workflow intelligent and cumulative, rather than isolated and forgetful. Before diving into code, let's get a quick overview of how LangGraph updates its state. There are three main update patterns: replace, accumulate, and merge, each serving a different purpose.

Replace simply means the old value is overwritten by the new one; the state is refreshed with updated information. Accumulate allows the state to grow as your workflow progresses; it builds up information step by step, capturing outputs from multiple nodes or iterations. Merge brings different pieces of information together; it integrates updates into the existing state so that nothing useful is lost. Together, these update types define how your workflow maintains continuity, builds knowledge, and keeps its context consistent throughout execution. Let's see how to create your state schema using TypedDict.

Here's a state definition example for a research workflow. We import TypedDict from Python's typing module, then define a class called ResearchState that inherits from TypedDict. Each field has three important elements: a clear name that describes what it holds, a type specification that Python can validate, and a purpose in the workflow that makes it obvious why it exists. This is your state schema, your contract for what data flows through the graph. Every node will receive this state structure, can read from any field, and can update any field it needs to. Let's follow the journey of how state moves through nodes, step by step. Here's the step-by-step flow. We begin with initial state at start.

The state contains the query: "What are AI trends?", but web_results, doc_results, and final_answer are all empty strings. The step_count is 0 because we haven't processed anything yet. This is your starting point: minimal information, ready to be enriched. Now watch what happens after node 1 processes the web search. The query stays the same: "What are AI trends?", because that doesn't change, but now web_results has content: "LangGraph adoption growing..." The node 1 did its job and added what it found. The doc_results and final_answer are still empty because we haven't reached those nodes yet, and step_count is now 1, tracking that we've completed one processing step.

Notice how state is growing, accumulating knowledge. Node 1 didn't erase anything; it added to what was there. This is the power of state flow. The journey continues as state flows forward, building knowledge at each step. After node 2 completes the document search, everything from before is still there: the query, the web_results from node 1. Now doc_results has been populated: "RAG systems popular...", node 2 searched internal documents and added its findings. The final_answer is still empty; we're not ready to synthesize yet, and step_count is now 2, showing our progress.

But now final_answer has been filled in: "Key AI trends include...", node 3 looked at everything that came before, combined the web findings and document findings, and created a comprehensive answer. State started with just a question; each node added its piece. By the end, state contains the full story: what was asked, what was found from different sources, and the final synthesized answer. When you return a simple value like "step_count": 5, it completely overrides the previous value. If step_count was 3, it's now 5. This is straightforward replacement: the new value replaces the old.

Pattern 2 is add to list, or accumulate. This is more sophisticated. By using Annotated [list, add], you tell LangGraph to append to the list rather than replace it. When your state field is a dictionary, returning {"metadata": {"author": "AI"}} merges it with the existing metadata dictionary. Previous keys stay, new keys are added, and matching keys get updated. These three patterns give you complete control over how state evolves. Choose replace for simple updates, choose add for accumulation, and choose merge for complex nested data. Third, current_step as a string; this tracks which node is running, using simple replacement since only one step is current at a time.

Fourth, progress as an integer; this might go from 0 to 100. Simple replacement works perfectly. Fifth, Summary as a string: the final output, replaced once when synthesis is complete. And sixth, confidence as a float as score from 0.0 to 1.0, also using simple replacement. This design shows best practices, unchanging inputs are simple types, accumulating data uses Annotated with add, and tracking variables use simple replacement. Good state design makes your workflow clean, predictable, and powerful.

Before we wrap up, let's cement the key principles of state flow. Remember these 5 principles. First, state is shared: all nodes access the same state object. There's no hidden information; everything is visible to every node. Second, state accumulates: information builds up over time; each node adds to what came before, creating a growing pool of knowledge. Third, state is typed: TypedDict provides structure and validation. You define exactly what fields exist and what types they should be, preventing errors and confusion.

Fourth, nodes read and write: each node can see all previous work that earlier nodes completed, and it can add its own contributions to the state. Fifth, state flows forward: like a river, it moves in one direction through the graph; it doesn't go backward. It progresses from start to end, accumulating as it goes. These principles are what make LangGraph workflows so powerful and controllable. State is the thread that ties your entire workflow together, carrying context and knowledge from beginning to end.

If it's historical data, route to document search to query your knowledge base, then end. If it's comprehensive research, route to both web plus docs to search both sources, then end. Why is this conditional? Because different queries need different approaches.

A question about today's stock market needs web search; documents would be outdated. A question about our company's Q3 results needs document search; its internal information. A question about industry trends and our position needs both sources for a complete answer. The workflow adapts its behavior based on the input. This intelligence and adaptability is what makes conditional workflows so powerful for real-world AI applications. Let's now compare the two patterns to understand when to use each.

Linear workflows are best when: first, your process is consistent, the same steps always apply; second, no variations are needed, one size fits all; third, simplicity is important, you want easy-to-understand workflows; fourth, easy debugging is a priority, you want clear sequential logic. Examples include ETL pipelines, where you always extract, transform, then load, or report generation, where the format never changes. Conditional workflows are best when: first, different inputs exist, not all requests are the same; second, adaptive behavior is needed, you must respond differently based on context; third, intelligence is required, the system should make smart decisions; fourth, efficiency through routing matters: why search documents if you only need web results?

Examples include chatbots that handle different intents, classifiers that sort inputs, and smart assistants that adapt to user needs. Here's a simple rule of thumb: if you can write your workflow as a numbered list that never changes, use linear. If you find yourself saying "it depends" or "if this, then that," use conditional. Both patterns are essential tools in your LangGraph toolkit.

The ReAct pattern combines 3 phases. The agent reasons step by step, takes actions in between, and processes feedback to guide its next step. Rather than separating planning from action, ReAct blends them. Thinking evolves as the agent interacts with the environment or tools. This design enables adaptive, reflective behavior. The agent doesn't commit to a plan blindly. It adjusts as it goes. Every ReAct process begins with a goal, like answering a question, solving a task, or completing a workflow.

To get started, the agent begins by thinking aloud. It breaks down the goal into parts, infers what it knows, and identifies what it still needs to find out. This reasoning leads to an intermediate thought. Next, the agent decides on the best next step and performs an action such as retrieving information or testing a hypothesis. After acting, it examines the outcome. Did the action succeed, fail, or reveal something new? Based on this, the agent observes feedback and updates its reasoning.

The loop continues. Reason, act, observe, reason until the task is complete or no further steps are needed. Let's now consider ReAct performing a real-world task, such as an AI travel agent helping a user find a budget-friendly flight to Delhi. The agent begins by reasoning, the goal is to fly on a weekend and stay under budget. It wants to check weekend flights to Delhi under ₹10,000. It forms an initial plan based on that thought. It acts by querying a flight search API with those parameters.

When the tool returns no valid flights, that becomes feedback. The agent then updates its thinking. It reasons again. Perhaps it should relax constraints, like increasing the budget or considering alternate options such as flying on weekdays. From there, the agent continues reasoning and acting until it finds a valid flight and completes the task. So with this knowledge in mind, you may wonder when should you use the ReAct framework?

In general, ReAct tends to shine in situations where agents must adapt and reason progressively, like answering questions or planning actions dynamically. In particular, agents that interact with APIs, databases, or dynamic environments benefit from ReAct's adaptive flow. On the other hand, ReAct may introduce unnecessary overhead and simpler or high-speed tasks where direct execution is sufficient. As we wrap this video, it's worth noting that ReAct is thoughtful and adaptive.

For example, ReAct agents don't separate thinking and doing. They alternate between the two, learning as they go. This loop creates space for hypothesis testing, error, internal reflection, and correction. These are hallmarks of intelligent behavior. If your agent needs to explore, learn, and adapt, ReAct is a powerful and reusable pattern to start with. This makes it a great framework for dynamic, tool-rich, or uncertain environments.

In complex tasks, accuracy doesn't just come from knowledge, it comes from reasoning through intermediate steps. By making agents think out loud, we can trace their logic, catch errors, and improve confidence in their outputs. To support this, two key reasoning patterns, Chain-of-Thought and Tree-of-Thought, are commonly used. These patterns help structure how agents think, either linearly, step-by-step, or with branching exploration. Together, they form the backbone of reasoning in many modern agentic systems.

Chain-of-Thought is like a step-by-step explanation where each new idea builds directly on the previous one. It is built on linear reasoning, where one thought leads to the next. It's especially effective in tasks like solving math problems, analyzing arguments, or following multi-step instructions. Each reasoning step is explicit, which helps both humans and tools check for errors or understand how a conclusion was reached. It makes intermediate thinking both visible and auditable.

Tree-of-Thought, on the other hand, encourages agents to consider several possibilities at each step, rather than just following a single path. The agent explores, reflects on, and scores these branches, then selects the most promising path forward. When there's no clear right answer or multiple strategies to compare, Tree-of-Thought is a powerful reasoning model. For example, it can be used for creative tasks, planning, and strategic decision-making. Let's now compare Chain-of-Thought and Tree-of-Thought reasoning patterns.

While both aim to make agent reasoning more transparent and reliable, they differ significantly in how they explore and evaluate ideas. Chain-of-Thought follows a linear sequence of steps. The agent builds its reasoning one step at a time in a straight line. In contrast, Tree-of-Thought enables branching exploration. The agent considers multiple paths or possibilities before choosing the best one. Chain-of-Thought is ideal for tasks that require step-by-step logic, like solving math problem and/or logical puzzles. Tree-of-Thought is better suited to tasks that benefit from planning, creativity, or strategy, where multiple directions need to be evaluated.

Because Chain-of-Thought (CoT) progresses linearly, its transparency is high. We can easily follow the logic step-by-step. Tree-of-Thought (ToT) is medium to high in transparency, well, it offers visibility into multiple reasoning paths, it can be harder to track due to its complexity. Chain-of-Thought does limited exploration. It commits to one path of reasoning. Tree-of-Thought, on the other hand, encourages high exploration, allowing the agent to simulate different approaches before committing to one. ToT relies on sequential reasoning. Each step builds on the last, and decisions are made one at a time.

ToT supports parallel evaluation where multiple reasoning paths are developed, scored, and compared to select the strongest output. Together, these two patterns equip agents with complementary strengths. CoT brings precision and clarity, while ToT introduces flexibility and depth. The choice depends on the nature of the task, structured execution, or exploratory planning. Let's now compare both reasoning styles on a creative task, naming a green laundry brand. Chain-of-Thought might move in a logical, direct path, define attributes, and map to relevant keywords.

Tree-of-Thought, on the other hand, explores entirely different themes, ideation strategies, and creative directions. While both are useful, Tree-of-Thought is better when breadth and innovation are required. To recap these ideas, there are two paths to smarter reasoning. For example, use Chain-of-Thought when your agent needs to clearly explain its reasoning and move toward a known goal step-by-step. It is simple, reliable, and traceable. However, use Tree-of-Thought when the agent benefits from comparing multiple directions before committing.

This approach is exploratory, flexible, and creative. Put another way, for structured problems, go linear. For strategic or creative work, branch out. In dynamic environments, agents don't just execute, they learn and adjust. Real-world agents face uncertainty and evolving conditions in their surroundings. In this video, we will identify agent patterns that incorporate feedback loops and modify future actions accordingly. Let's break down the types of feedback an agent can receive and how they shape its behavior.

External feedback comes from outside the agent, from the user, or the environment. This might look like a user clicking a thumbs down on a response, an API call that fails due to a timeout or invalid input, or an external system returning a confidence score that's too low. These signals tell the agent that its output may be flawed or incomplete and prompted to rethink or retry its approach. Internal feedback originates from the agent's own reasoning process.

It might detect contradictions in its logic, realize that its confidence in a decision is unusually low, or identify missing information it needs to proceed. This self-awareness allows the agent to flag uncertainty and either pause, reflect, or escalate the task. Importantly, feedback doesn't always arrive as a direct instruction. Sometimes it's explicit, like a user saying that's wrong. Other times it's implicit, such as a tool returning an empty result or the agent noticing that it's repeating itself. Robust agent design requires detecting and acting on both kinds of signals.

Together, these types of feedback form the backbone of adaptive intelligence, helping agents evolve, self-correct, and improve their outcomes over time. Now let's look at some common patterns where feedback isn't just observed, but actively shapes what the agent does next. One of the simplest and most effective feedback-driven patterns is the retry loop. When an action fails, like an API request timing out or a tool returning an error, the agent doesn't give up. Instead, it retries the action, often with slightly modified inputs or after a brief delay.

This kind of resilience is essential when working with unstable or unpredictable environments such as live APIs or network-dependent tools. Sometimes agents need to adapt not because of failure, but because the context has changed. Maybe the user clarified their request or a new constraint emerged mid-conversation. In this case, the agent modifies its prompt or internal plan to account for the updated context. This kind of dynamic responsiveness ensures the agent doesn't stubbornly follow outdated instructions, but instead adjusts in real-time.

And when retrying or adapting isn't enough, feedback patterns can trigger escalation. The agent might transfer control to a more capable peer, say, moving from a general agent to a specialist one, or it might signal for a human to step in. This handoff ensures that when complexity or risk exceeds the agent's confidence or capabilities, someone else, machine or human, can take over. Together, these patterns show how agents can behave more like intelligent collaborators, not just static responders.

By embedding feedback-driven behaviors, we build systems that don't just react, they recover, adapt, and escalate when needed. Imagine an agent answering complex questions. The loop continues until the confidence score is high or the user confirms success. Feedback isn't just an add-on. It's essential to building agents that learn and adapt. Whether they retry, reroute, or refine. Feedback-driven agents are more resilient, more intelligent, and more human-like in how they respond to the world.
